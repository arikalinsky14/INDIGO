# CHROMA-FlexMat: Flexible-Material Adaptation Scaffold

This is a scaffold of the four foundational modules that change going from
the original CHROMA-Lite (fixed 25-material vocabulary) to a flexible-material
RGB→Structure model where the user provides any pool of materials at
inference time, given as their refractive-index data (n, k vs wavelength).

The scaffold is **runnable end-to-end on toy data** (each module has a
`__main__` smoke test) but is **not yet wired to your training data
pipeline**. The remaining porting work is listed at the bottom.

## What's in here

```
chroma-flexmat/
├── src/
│   ├── material_features.py    # Load JLL CSVs, resample to canonical grid, featurize
│   ├── synthetic_materials.py  # 3 strategies for synthetic n,k generation
│   ├── materials_vocab.py      # Slot-indexed token encoding (replaces fixed-vocab)
│   └── optical_sim_flex.py     # Optical simulator that accepts arbitrary n,k
└── pretrain_rgb_to_structure/
    └── src/
        └── model.py            # FlexMaterialMLP — shared encoder + masked output
```

All modules use **absolute imports from `src.*`** per the project convention.

## How the pieces fit together

```
                  user provides
                  ┌──────────────────┐
                  │  Material pool   │  list of (name, n[128], k[128])
                  │  (≤ M_MAX = 32)  │  on the canonical wavelength grid
                  └────────┬─────────┘
                           │ featurize_pool + pad_pool_features
                           ▼
              ┌──────────────────────────┐
              │ pool_features [M_MAX,2,L]│
              │ pool_mask     [M_MAX]    │
              └──────────┬───────────────┘
                         │
       target RGB        │     structure-so-far
       [3]               ▼              [M_MAX, MAX_LAYERS]
        │      MaterialEncoder (shared)        │
        │      → [M_MAX, encoder_out]          │
        │      *= pool_mask                    │
        │                                      │
        └──────────┬──── concat ───────────────┘
                   ▼
          Backbone MLP (RGB-to-Structure-style)
                   │
                   ▼
              logits [VOCAB_SIZE]
                   │
                   │ + output_mask (–∞ for invalid slots)
                   ▼
              softmax → next-token distribution

         token_id = slot_idx * NUM_THICKNESSES + thickness_idx
                   or EOS

         decode using user's pool: pool[slot_idx].name and the thickness
```

`VOCAB_SIZE = M_MAX * NUM_THICKNESSES + 1 = 32 * 40 + 1 = 1281`
(vs. 1001 in original CHROMA-Lite).

## Why this prevents overfitting to specific materials

1. **Shared material encoder** — the encoder MLP is applied to every slot
   with the same weights. The model has no slot-specific capacity, so it
   cannot learn "slot 3 = Ag". Anything it learns about a slot must be a
   function of n, k features.

2. **Slot indices are arbitrary per example** — at training time, when you
   randomize slot ordering for the same underlying structure, the model
   gets the same RGB target with completely different "slot 3 = Ag at
   100nm" → "slot 7 = Ag at 100nm" tokenizations. The only feature
   shared across these is the n,k spectrum at the chosen slot. This is
   the strongest pressure toward feature-based generalization.

3. **Synthetic materials in `synthetic_materials.py`** — by generating
   ~80% of training materials from Lorentz oscillators, perturbations of
   real materials, and pair interpolations, the model never sees a
   stable list of distinct material identities to memorize. The JLL
   library becomes a rare special case rather than the dominant training
   signal.

4. **Held-out real materials** — by partitioning the JLL library into
   training and validation halves, you get a direct measurement of
   generalization to materials never seen during training. This is the
   number that actually matters for grant-proposal claims.

5. **Output masking** — invalid slots get `-inf` logits, so the model
   cannot "leak" probability mass to slots that don't exist for the
   current example. This forces honest behaviour at variable pool sizes.

## Recommended dataset generation pattern

For each training row generated by `create_dataset/`:

1. Sample `pool_size` uniformly from `[max(2, n_layers), M_MAX]`.
2. Compose a pool by drawing:
   - `n_layers` materials guaranteed to appear in the structure (drawn
     from a mix of held-in real + synthetic; the structure layers are
     drawn from these).
   - `pool_size - n_layers` distractor materials (also synthetic + real).
3. Shuffle the pool slot ordering. Reassign each layer's slot index
   accordingly.
4. Run the optical simulator on the resulting structure to get the
   target RGB.
5. Serialize: `(rgb, pool_features [M_MAX,2,L], pool_mask [M_MAX],
   structure [M_MAX, MAX_LAYERS], target_tokens, pool_size)`.

The slot-shuffling step in (3) is the single most important defense
against material memorization — it makes slot indices uninformative
without n,k features.

## Validation strategy (two-tier)

Hold these out from training entirely:
- **Tier A** (seen materials, unseen structures): pools drawn from the
  same distributions as training, but the (RGB, structure) pair is novel.
  Measures generalization to new color targets.
- **Tier B** (unseen materials, unseen structures): pools include held-out
  real materials and a held-out synthetic distribution (e.g. only Lorentz
  with oscillator counts the model wasn't trained on, or only `aSi-Zarei`
  family). Measures generalization to *new* materials.

The Tier-A vs Tier-B gap quantifies how much of your model's apparent
performance comes from material memorization vs. genuine n,k
generalization.

## Remaining porting work

These existing CHROMA-Lite scripts need adaptation. Most are minimal
diffs since the new modules deliberately mirror the original API.

### `create_dataset/` — needs the most rework

The new dataset row format includes the material pool, not just a
material/thickness pair list. Either:

- **Recompute everything**: swap `create_dataset/src/random_layer.py` and
  `compile_datasets.py` to draw materials from the held-in real + synthetic
  union, sample pool sizes, shuffle slot ordering, and write the new
  parquet schema:

  ```
  rgb_R [3 ints]
  pool_size [int]
  pool_material_names [list of strings, length M_MAX, padded with ""]
  pool_n [list of [NUM_LAMBDA] floats, length M_MAX]
  pool_k [list of [NUM_LAMBDA] floats, length M_MAX]
  layer_slots [list of int, length n_layers]
  layer_thicknesses [list of int, length n_layers]
  num_layers [int]
  ```

- **Lightweight version for early experiments**: store n,k as references
  to a shared synthetic-material library, not in every parquet row.
  Saves disk space dramatically. Each row stores a pool_id which indexes
  into a sidecar parquet of pool definitions.

### `src/dataset.py` — rewrite

`ThinFilmDataset` becomes `FlexThinFilmDataset` with these changes:
- Each iter step yields all of: rgb, pool_features, pool_mask,
  structure_matrix, target_token, pool_size.
- The collate_fn from `pretrain_rgb_to_structure/scripts/training.py`
  expands one example into N+1 autoregressive samples; this logic ports
  over but each sample now carries the same pool throughout.
- File scanning, deterministic permutation, and the 99.5/0.5 split logic
  port unchanged.

### `pretrain_rgb_to_structure/scripts/training.py` — minimal diff

The training loop body is largely unchanged. The diffs are:
- `compute_loss(model, rgb, structure_matrix, target_token)` →
  `compute_loss(model, batch)` where batch is the full dict.
- The collate_fn in this file needs to thread `pool_features`,
  `pool_mask`, `pool_size` through the autoregressive expansion (same
  values for all N+1 expanded steps).
- LR warmup + cosine decay, AdamW, grad clipping, checkpoint saving:
  unchanged.

### `pretrain_rgb_to_structure/scripts/evaluate.py` — minimal diff

- Teacher-forcing eval: same shape, just pass the new batch dict.
- Autoregressive eval: replace the call to `generate_structure` with the
  new signature in `model.py`. The CIEDE2000 / color swatch / sampling
  modes carry over unchanged.
- Optical sim call: replace `OpticalSimulator(...).compute_color(materials,
  thicknesses)` with `FlexOpticalSimulator(...).compute_color(pool,
  slot_indices, thicknesses)`.

## Recommended next steps

1. **Verify the synthetic distribution by eye**: plot 50 perturbed,
   50 interpolated, 50 Lorentz materials (n vs λ and k vs λ) and check
   that none look pathological. The smoke tests verify physical bounds
   but won't catch e.g. interpolated metal/dielectric pairs producing
   nonsensical hybrids.

2. **Verify the canonical grid alignment**: compute the same structure's
   color via `OpticalSimulator` (original, named-material) and
   `FlexOpticalSimulator` (new, n,k-direct) and confirm they agree to
   within 1 sRGB unit. Any discrepancy reveals a wavelength-grid
   misalignment.

3. **Wire up the dataset** following the schema above. Start small — a
   few hundred examples is enough to verify end-to-end training before
   committing CRC SUs to a full run.

4. **Run the LR search** at the new model size (~1M params with M_MAX=32,
   d_model=1024 — actually closer to 4M). The original LR power-law
   fit will not transfer; expect to redo `lr_tuning.py` from scratch.
