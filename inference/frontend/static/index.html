How an INDIGO solve works

      
    

    

      solve(model, pool, spec) → Result. Six
      stages in order. Hyperparameter callouts are in purple.
    


    
    

      
  1. 1
    
        
    parse (prompt mode only)
    
        
    If you used the Prompt tab, your text goes through the LLM
        (parse.py) which emits a structured
        spec: target Lab + constraint list. Three validation gates
        (schema / semantic / physical) reject malformed output.
    
      
    2. 

      
  2. 2
    
        
    encoding pool
    
        
    The pool of materials (≤ M_MAX = 32)
        is encoded into the model's slot-token representation. Runs once per
        request. Negligible cost on the wall-clock.
    
      
    3. 

      
  3. 3
    
        
    sampling ensemble — Ensemble N, Temperature
    
        
    The model autoregressively decodes N
        candidate structures in one batched forward, conditioning on the
        target Lab + pool. Higher N = more
        diversity; Temperature controls how
        confidently the model picks each layer. Constraint masks fire here
        (allowed_subset, layer_count, total_thickness running budget,
        symmetry, …) so feasibility is by construction.
    
      
    4. 

      
  4. 4
    
        
    simulating candidates
    
        
    For every unique candidate after de-duplication, the JLL
        transfer-matrix physics computes reflectance & achieved Lab,
        then ΔE_00 vs target. This is the dominant CPU cost — the
        physics chain is sequential per candidate (a known constraint
        documented in simulate.py).
    
      
    5. 

      
  5. 5
    
        
    selecting top-k — Top-k, Tolerance %, Weight λ
    
        
    Candidates are scored by J = ΔE + λ·R_l2
        where R_l2 is a gradient-based robustness prediction (skipped when
        Tolerance % = 0). The top
        Top-k by J are kept as alternatives.
    
      
    6. 

      
  6. 6
    
        
    refining top-k — Refine top-N, Refine iters
    
        
    Each of the first Refine top-N
        candidates gets a projected-Adam local search on continuous
        thickness (within constraint bounds), minimising ΔE. Up to
        Refine iters steps; terminates
        early if ΔE plateaus. On CPU this is the slowest single stage —
        each iter is a forward + grad call through the JLL physics. With
        Refine top-N = 1 and
        Refine iters = 25 you're at the
        sweet spot for laptop speed; turn both up for production-quality.
    
      
    7. 

      
  7. 7
    
        
    finalising — MC samples
    
        
    If MC samples > 0, K Monte-Carlo
        thickness perturbations resample ΔE on each refined candidate to
        compute p50 / p95 / worst robustness numbers. Then candidates are
        re-ranked by J (refinement may have shifted them), the chosen pick
        is wrapped in a Result envelope
        with provenance, and returned.
    
      
    8. 
    


    

      
Speed cheat-sheet (CPU laptop):

      
    
        
  • N=100, top_k=1, refine_top_n=1, refine_iters=15, tolerance=0 ⇒ ~5-10 s, "fast" preset
    • 
        
  • N=150, top_k=3, refine_top_n=1, refine_iters=25, tolerance=0 ⇒ ~15-25 s, default
    • 
        
  • N=500, top_k=5, refine_top_n=3, refine_iters=80, tolerance=5, mc_samples=16 ⇒ ~2-5 min, "best" preset
